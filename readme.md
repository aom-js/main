> Текст ниже — исторические заметки автора: замысел и ход размышлений, а не описание текущего поведения. Расхождения заметок с кодом перечислены в разделах «Расхождения с историческими заметками» документов пакетов.

Ядро `@aom` наследует общий принцип уже существующей концепции `aom` и позволяет запустить `state-machine` вокруг схем данных.

Таким образом задача сводится к тому, чтобы обогащать контекст изолированных состояний контроллеров вокруг хранилища данных.

В общем смысле, ядро должно позволять создавать такую структуру в памяти, используя при необходимости `static` свойства классов для хранений промежуточных состояний.

В общем смысле это остается все та же последовательность маршрутов, которые проецируются в методы REST-API, со спецификацией OpenAPI, либо GraphQL, либо Firebase.

Также меняется концепция построения цепочек вызовов: теперь это становится `rxjs` каскад, который можно будет рефлексировать и перехватывать в случае ошибок.

Таким образом чисто технически становится неважен движок, на котором это все выполняется, миграция осуществляется за счет генерации списка ендпоинтов с последовательностью `rxjs` процедур над указанным контекстом. То есть должна быть нативная совместимость с произвольно взятыми http-серверами, и должна обеспечиваться переносимость контекста.

То есть, как должно быть организована базовая логика:

1. сохраняется концепция декораторов, которые формируют ендпоинты, также активно используется механика `Nextpoint`, которая позволяет из конкретного ендпоинта выйти на замыкающую
2. для декораторов аргументов вида `Body`, `Query` и `Headers` и прочие данных на контексте используется обертка, которая говорит, из какого элемента аргументов брать значения
3. механика описаний сущностей такова, что должна иметь возможность повторно использоваться в случае различных codegen процедур.

## Core

Само ядро используется для того, чтобы создавать обертки для декораторов, которые сами по себе создают релевантные сущности, и могут быть соответствующим образом использованы для как связанные компоненты с соответствующими описаниями.

При этом ядро хорошо работает для собственно класса и статичных методов, но в него бы идеально еще запихнуть возможность создавать декораторы вокруг методов инстанса и просто свойств.

Проблематика подхода со свойствами такова, что когда я создаю обёртку для метода, то саму обёртку я делаю для значения `class[property]`, то есть конкретной функции, которая становится ключом в WeakMap. Чисто технически я могу позволить себе сделать тоже самое для методов инстанса. То есть я могу обратиться к записи через `AOMCore.instance(class[property])`, и получу корректное значение после того, как оно было создано через `AOMCore.instance(class, property)`.

Однако остаётся открытым вопрос с тем, как взаимодействовать с конструкциями, которые являются свойствами, и не являются функциями. В этом случае для хранения соответствующего инстанса следует, по всей видимости, создавать какой-то свой собственный ключ, который будет храниться в собственной карте по релевантному ключу. То есть должна быть конструкция, которая, видимо, через двойной `map.set/map.get`, получая на вход target и property будет возвращать и создавать уникальную запись, которую можно будет использовать в качестве ключа в weakmap.

## Кодогенерация

Итак, где будет задействована кодогенерация? Обрисуем самые очевидные случаи:

- openapi-спецификация из роутеров
- экспорт изоляторов (?)
- генерация собственного структурного кода как api-библиотеки, которая позволит создавать плотные интеграции вокруг API.

Как можно и нужно решать эту задачу?

Для начала следует систематизировать те кейсы, в которых вообще задействованы "сторонние" данные. И, вероятно, чисто технически подвести всю логику под то, что будут задейстованы свои собственные декораторы, благодаря которым будет происходить соответствующая рубрификация и систематизация.

В настоящий момент (в бете `aom`) для этого используется декоратор `@ComponentSchema`, который регистрирует релевантный класс в сопутствующем пространстве мета-данных, и потом позволяет получить все значения оттуда, и выгрузить их "общим" списком. При этом генерируются избыточные данные, которые там вообще не нужны.

Однако, для тех же схем OpenAPI требуется сохранить механику, которая будет создавать компонентые отсылки. А также делать связи компонент между собой при их вложении друг в друга.

Следующая проблема, которую надо суметь решить - это использование различных способов генерации тех самых схем данных. В частности есть варианты, когда они могут быть сделаны через `class-validator`, `zod`, `typebox` и им подобные библиотеки. И в разных случаях будут использоваться разные механики обращения к данным. То есть чисто технически следует в первую очередь правильно систематизировать такие структуры для обеспечения удобного доступа к структурам.

### Как это можно заставить работать?

В первую очередь, если говорить о генерации OpenAPI, следует точно понимать, что у нас есть свойство `schema`, которое ожидается в соответствующих декораторах, и на которое я могу опираться, выполняя соответствующие проверки. При этом финальным значением в этом свойсте может быть как собственная `json-schema`, так и `$ref`-ссылка на общий справочник.

Что важно, `$ref`-ссылкой может быть также значение какого-то элемента `json-schema`, которые генерируется в списке компонент. Что создает требования для контроля соответствующего каскада.

То есть, надо двигаться от того, как идентифицировать значения к тому как их "рендерить" в каждом конкретном случае.

Рассмотрим вероятные примеры, каким может быть соответствующий код. Буду отталкиваться от того, что могут использоваться `class-validator`, `zod` и `typebox`, как наиболее популярные инструменты схемоописания. А также буду исходить из того, чтобы не писать свои библиотеки трансформаций, а оформить структуризацию таким образом, чтобы можно было использовать набор готовых компонент, чтобы достичь требуемого результата.

В первую очередь, полагаю, следует начать с того, что надо объявить и настроить свои собственные функции "регистрации" данных. Возможно, будут также использоваться какие-то преднастроенные паттерны, но так или иначе это должно прийти к тому, что, как и в случае с изоляторами, настраивается `get/set` логика, формирующая соответствующие связи и возможности.

Итак, задачу следует решать одновременно с двух сторон: с понимания того, как конечное значение будет видно на стороне генерации, и настройка инициирующих данных к тому, чтобы получить требуемое значение в конце.

Рассмотрим наиболее горячий пример, с которого требуется начать: OpenAPI-схемы. Конечной точкой, где будет приниматься конечное решение о той или иной визуализации будет перечисление конкретных значений в `openapi`-свойстве, инициируемым декоратором, где будут значения `schema`, требующие конкретной визуализации.

То есть, в качестве конкретного значения там может быть как установленная `json-schema` (в том числе, отсылка на `$ref` в соответствующем справочнике.), так и объект определенного типа, для которого следует выполнить определённую команду преобразования. Результатом этого преобразования может быть как получение `json-schema` значения, так и `$ref` отсылка. Но самое главное здесь то, что требуется выполнить соответствующую проверку универсальным образом и предельно прозрачно для разработчика. При этом, чтобы соответствующее поведение было надежным, предсказуемым и всегда давало корректный результат.

Для этого следует понять, как данная ситуация должна выглядеть на стороне определения структур данных и их конфигураций.

Составим несколько базовых примеров на базе `class-validator`, как наиболее чаще применяемой, и совместимой с типизацией схем в базе данных, а также форм, поисковых фильтров и так далее.

```ts
@ComponentSchema()
class Response extends CommonResponse {
  @IsString()
  value: string;

  constructor(value: string) {
    this.value = value;
  }
}

class Controller {
  @Get()
  @Responses(Response.JSONSchema())
  static async Value() {
    return new Response("test");
  }
}
```

Значение `Response.JSONSchema` сгенерирует структуру вида примерно из следующей функции

```ts
export function responseJsonSchema<T extends C.Class<any, any>>(
  schema: T,
  description?: string | string[],
  status?: number
): OpenApiResponse {
  return {
    status: status,
    schema: schema,
    isArray: Array.isArray(description),
    description: description ? description.toString() : "",
  };
}
```

Таким образом в момент выполнения действия по конкретному показу того, чем является данная схема (а там может быть в том числе `RefContainer` или анонимная функция, возвращающая класс в результате своего выполнения), проверяется её присутствие в соответствующих описательных местах. И в зависимости от её наличия там выполняется операция по корректному получению того значения, которое будет помещено в данное место и данный вызов.

То есть, для значения `schema` будет вызвана некая типовая проверка от базового класса описаний, где эта схема в принципе должна быть зафиксирована, и для которой должно быть установлено конкретное преобразование. А для этого требуется использовать какой-то типовой паттерн, который при декорировании соответствующего класса точно и чётко укажет, что и в какой последовательности с ним будет происходить.

При этом при генерации релевантной записи должно происходить фактически 2 действия: запись непосредственного значения в схеме, и если там используется `$ref`, то запись в соответствующем месте со справочником. В котором вложенные структуры также должны проходить 2 этапа.

Итого, теперь следует вернуться к началу, и понять, что это такое будет.

Скорее всего, будет также использоваться декоратор `ComponentSchema`, который дополнится конфигурацией, объясняющей правила рендеринга значений. И, что важно, должен также использоваться дополнительный декоратор для свойства, который будет характеризовать наличие связи там, где она есть.

И тут, вероятно, будут достаточно специфические ситуации, которые надо будет грамотно разрулить. И еще, возможно, данный принцип можно будет использовать для валидации данных в body и query. Но это неточно.

Начнем с того, что из себя будет представлять конфигурация, которая, вероятно, будет устанавливаться один раз на весь проект, но чисто технически должна иметь возможность быть множественной, и создаваться в рамках одного единственного набора критериев, характеризующих способы интерпретации данных.

Представим принцип, каким должна формироваться конфигурация, чтобы она корректно могла быть использована "внутри".

Допустим, есть компонента `@aom/json-schema`, которая возвращает декораторы и некие конфигураторы, которые в целом совместимы со всеми прочими логиками внутри фреймворка.

```ts
import { ComponentSchema, JSONSchema, ComponentSchemaConnect } from '@aom/json-schema';
// создание конфига
const config = new JSONSchema({ ... });
// установка по умолчанию
JSONSchema.default({ ... })

@ComponentSchema(config)
class Response extends CommonResponse {
  @IsString()
  value: string;

  constructor(value: string) {
    this.value = value;
  }
}

```

Чем будет являться конфигурация? Во-первых, это фиксация некой функции, благодаря которой будет извлекаться `json-schema` из входящего класса. То есть, некая `render`-функция. В случае использования `class-validator` это будет примерно так

```ts
import { targetConstructorToSchema } from "class-validator-jsonschema";
import { SchemaObject } from "openapi3-ts/oas30";
import { defaultMetadataStorage } from "class-transformer/cjs/storage";
import { refPointerPrefix } from "./component-schema";
import { SchemaConverter } from "class-validator-jsonschema/build/defaultConverters";

JSONSchema.default({
  render(target: ClassConstructor) {
    return targetConstructorToSchema(constructor, {
      additionalConverters,
      classTransformerMetadataStorage: defaultMetadataStorage,
      refPointerPrefix,
    });
  },
});
```

Для этого надо снова посмотреть на ситуацию с конечной точки зрения. То есть понять, что будет происходить на выходе для того, чтобы паззл сходился со всех сторон сразу. Полагаю, для этого надо начать писать сам код, и решать его, например, для кейса того же `class-validator`, что позволит свести механику в общую кучу, ну и как минимум прощупать почву под искомое решение.
