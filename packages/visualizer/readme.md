# `@aom-js/visualizer`

Пакет строит по дереву контроллеров граф API — маршруты, цепочки звеньев и компонентные схемы с их связями — и рендерит его в одну самодостаточную HTML-страницу. Страница отдаётся обычным endpoint-ом, поэтому карта живёт внутри самого модуля API рядом с `/openapi.json`. Состояние на 2026-09-03.
Читать до: `packages/router/readme.md` (мета-модель, курсоры, сборка маршрутов), `packages/schemer/readme.md` (компонентные схемы). Читать после: `packages/api/readme.md` (как endpoint отдаёт HTML). Термины — `test/docs/README.md#словарь`.

## Назначение и место в стеке

Роутер уже знает всё, что нужно для карты: `Router` разворачивает дерево бриджей в плоский список `AomRoute`, у каждого маршрута есть упорядоченная цепочка курсоров, а `OpenApi` вместе с `SchemasCollector` сводит компонентные классы в `components.schemas` с `$ref`-связями. Пакет ничего из этого не пересчитывает — он собирает данные в один сериализуемый граф (`VisualGraph`) и рисует его.

Ключевое решение: **граф всегда собирается на собственном экземпляре `OpenApi`**. Причина в том, как устроены отложенные декларации. Значения `openApi.*` (параметры билдеров, ответы, маркеры доступа) материализуются только в конструкторе `AomCursor` — до сборки маршрутов их в мета-инстансах просто нет (`packages/router/src/common/classes.ts:224-246`). Обойти дерево через `AomApi.instance(...)` без построения маршрутов недостаточно: получится структура без деклараций и с пустыми `route.markers`. При этом сборщик схем у роутера приложения общий на весь модуль, и поддерево из него не выделить. Поэтому `buildVisualGraph` строит свой `Router` на свежем `OpenApi` — это чистая сборка без ввода-вывода и без сервера, а курсоры создаются заново, так что живой роутер приложения не затрагивается (проверяется тестом «не ломает уже собранный роутер приложения»).

Отсюда же следует, что карта строится **от любого узла дерева**, а не только от корня: любой контроллер — валидный аргумент, для него собирается свой `Router` со своими префиксами.

Зависимости: `@aom-js/core` (`ClassType`), `@aom-js/router` (`Router`, `OpenApi`, `AomApi`, `AomRoute`) и `reflect-metadata`. Обратная зависимость одна: `@aom-js/api` использует пакет в `BaseVisualizerController`, поэтому в цепочке сборки визуализатор идёт **перед** api.

Пакет вводит два собственных термина: **граф** — структура `VisualGraph`, сериализуемый срез API; **звено** — элемент цепочки исполнения маршрута (курсор): middleware, nextpoint, маркер, хук инстанса или сам endpoint.

### Как собирается граф

1. `new OpenApi(...)` + `new Router(target, docs)`. Сокеты роутер в документ не кладёт — `buildVisualGraph` регистрирует их сам, иначе их схемы не попадут в сборщик.
2. Обход бриджей от корня даёт дерево контроллеров: префиксы, `pre`/`post`-middleware, хуки, маркеры, наследование. Повторный вход в уже раскрытый контроллер обрывается и попадает в `warnings` — циклический бридж не уводит обход в бесконечность.
3. Каждый `AomRoute` даёт `VisualRoute`: цепочка — из `route.cursors` (id, роль, точка прикрепления, порядковый номер), а параметры, тело, ответы, теги и защита — из уже собранной операции документа. Операция находится по ключу `метод:путь`, где путь пересчитан той же подстановкой `:param` → `{name}`, что делает `OpenApi.registerPath`.
4. Звенья агрегируются по всем маршрутам: `usedBy` — список маршрутов, в цепочку которых звено входит. Это и есть метрика «общности», по ней раскрашивается интерфейс.
5. Схемы разбираются из `components.schemas`: свойства с типами и признаками, а `$ref` (в том числе внутри `items`, `allOf`, `anyOf`, `oneOf`) становится ребром ER — `refs` в одну сторону, `referencedBy` в другую.
6. `declaredMembers` читает `_.origins` узла класса — единственный способ перечислить декорированные методы контроллера, не зная их имён. Так в карту попадают и звенья, объявленные, но никуда не подключённые.

### Страница

Документ самодостаточен: CSS, сценарий и сам граф вшиты внутрь, внешних загрузок нет (проверяется тестом). Граф лежит в `<script type="application/json">` с экранированными угловыми скобками — имя схемы или заголовок не могут закрыть блок.

Три колонки на панорамируемом полотне: контроллеры деревом по бриджам, маршруты, схемы данных. Поиск фильтрует блоки по пути, классу, методу и имени свойства.

В шапке блока две независимые операции, разведённые по элементам: **шеврон** сворачивает и разворачивает блок, **название** выделяет его. Клик по шеврону не всплывает, поэтому свернуть блок можно, не сбив текущее выделение, а выделить — не меняя того, что раскрыто. Esc сбрасывает выделение и поиск (из поля поиска первым же нажатием).

Выделение любого узла (звена, маршрута, схемы, контроллера) подсвечивает его окружение и гасит остальное: для звена — все маршруты, где оно встречается; для схемы — её замыкание по связям плюс маршруты-потребители; для маршрута — его цепочка и схемы. Подсвеченные блоки раскрываются автоматически, чтобы цепочку было видно сразу. Общие звенья дополнительно окрашены по числу использований и вынесены в боковую панель списком.

Линии рисуются в SVG поверх полотна: постоянно — связи схема→схема (собственно ER-слой), по выбору или по кнопке «все связи» — контроллер→маршрут и маршрут→схема. Полное отображение всех связей по умолчанию выключено сознательно: на реальном модуле это сотни рёбер, читать их нельзя.

## Как подключить

Пакет не содержит контроллеров и ничего не знает про HTTP — это осознанная граница:
визуализатор читает мета-модель, а маршруты объявляет тот слой, которому положено.
Есть два способа.

**Компонентой — там, где нужно.** Создаётся от маршрута, роутера или класса; корнем
карты становится корень роутера этого маршрута, то есть модуль, внутри которого
компоненту разместили:

```ts
@Get("/visualizer")
static Page(@Route() route: AomRoute): string {
  return new Visualizer(route).html;
}
```

`.html` здесь обязателен: `Server` отдаёт `text/html` только для значения типа
`string` (`packages/api/src/server/http.ts:177-179`), а объект уходит в JSON. Это
не случайность контракта — у компоненты есть и второй режим: `toJSON()` возвращает
граф, поэтому `return new Visualizer(route)` из endpoint-а отдаёт данные, а не
страницу. Сборка ленивая: пока не спросили `graph` или `html`, ничего не считается.

**Готовым контроллером из `@aom-js/api`.** `BaseVisualizerController` объявляет
`/visualizer` и `/visualizer.json` поверх той же компоненты; подключается бриджем
или наследованием, если нужны свои ограничения доступа:

```ts
@Controller()
@Before(AuthBasic.Required)
export class VisualizerController extends BaseVisualizerController {}
```

### Корень карты

Снаружи корень не параметризуется: ни query-параметра, ни отдельного маршрута для
поддерева нет. Страница получает граф целиком, а выбор узла — операция клиента через
`#root=ИмяКонтроллера`. Смена корня не порождает обращений к серверу и не перезагружает
страницу; ссылка с hash открывает нужный срез сразу.

Пути в срезе остаются абсолютными — это реальные адреса модуля, а не пересборка
дерева от нового корня. Сужается только состав: контроллеры, достижимые по бриджам,
их маршруты, звенья этих маршрутов и замыкание задействованных схем. Счётчик общности
звена пересчитывается внутри среза.

Программно тот же срез недоступен намеренно: `buildVisualGraph(SomeController)`
собирает **отдельный** граф от этого класса, с собственными префиксами — это другая
операция, и её результат не совпадает со срезом.

## Как использует приложение

`test/src/common/controllers/visualizer/controller.ts` объявляет `VisualizerController` поверх `BaseVisualizerController` из `@aom-js/api` и закрывает его тем же `AuthBasic.Required`, что и `/openapi.json`: страница раскрывает полную структуру API вместе с цепочками доступа. Бридж стоит на `ModuleRootController` (`test/src/common/controllers/module/controller.ts`), который наследует каждый `ModuleRoot`, поэтому `/visualizer` и `/visualizer.json` поднимаются на всех семи серверах приложения.

## Ограничения

- Сборка графа перестраивает дерево маршрутов на каждый запрос. Для модуля из ~75 маршрутов это единицы миллисекунд, кеша нет намеренно: карта должна отражать текущее состояние процесса.
- Маркеры маршрутов сериализуются через `JSON.stringify` как есть. Структура с циклом не роняет страницу — маршрут получает пустые маркеры, а причина попадает в `warnings`.
- Порядок бриджей в карте обратен порядку объявления: декораторы класса выполняются снизу вверх. Это поведение роутера, не визуализатора.
- Websocket-маршруты роутер в документ OpenAPI не кладёт; пакет регистрирует их сам, но декларации у сокетов обычно беднее, чем у http-маршрутов.
