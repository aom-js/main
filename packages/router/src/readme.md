# Работа с API в `@aom`

> **Черновик автора — исторический документ:** мысли на момент проектирования, а не описание текущего кода. Актуально — [`packages/router/readme.md`](../readme.md); расхождения заметок с кодом — [`architecture.md`](../../../docs/architecture.md#расхождения-с-историческими-заметками).

Итак, что будет являться главным отличием новой версии `aom` от старой?

- возможность работать с произвольно взятым фреймворком, который просто на своей стороне получит карту маршрутов, построенную контроллерами `aom`, и пробросит в них релевантный контекст
- возможность работать с произвольно взятыми структурами, определяющими типы данных, чтобы не ограничивать себя только лишь class-validator, а иметь возможность использовать `zod`, `typebox`, `ajv` и другие
- убраны лишние декораторы, оптимизированы некоторые референсы

## Порядок действий

В первую очередь надо постепенно перенести всю имеющуюся логику декораторов, постепенно убрав из них всякого рода повторы, систематизировав установку и возврат мета-данных, и всячески иначе актуализировать структурность.

## Настройка API

Прежде чем перейти к тому, чтобы делать декораторы параметров, следует определиться с механикой настройки API, где будет указываться, как именно прокидывается внутрь соответствующий контекст, как из него извлекаются полезные данные, и при необходимости помещаются обратно. А также используется индивидуальный контекст для сохранения `@This`-инстансов.

При этом в идеале следует сохранить механику, где внутрь могут помещаться штатные миддвари от фреймворка.

Для этого следует двигаться следующим образом. Рассмотрим то, как примерно это будет происходить на примере `koa`, `express`, а также `node:http` с наличием компонент, которые будут извлекать соответствующие значения из контекста.

Чтобы это понять, надо сформировать некое финальное представление интеграции полученной структуры маршрутов, которая в том числе связана с документацией, в существующую настройку http-сервера.

** пример для koa **

```ts
const server = new koa();
server.keys = [SESSION_SECRET_KEY];
server.use(koaBody({ multipart: true, formLimit: "50mb" }));
server.use(websocket());
// server.use(sessionMiddleware());
// server.use(sessionRestoreMiddleware());
server.use(cors({ origin: checkOriginAgainstWhitelist, credentials: true }));

const router = new koaRouter();

$aom.eachRoute(({ method, path, middlewares }) => {
  router[method](path, ...middlewares);
});

server.use(router.routes()).use(router.allowedMethods());

// standart 404 response if path wasn't found
server.use((ctx) => {
  ctx.body = new NotFoundResponse(PATH_NOT_FOUND);
  ctx.status = NotFoundResponse.status;
});
server.listen(settings.port);
```

** пример для express **

```ts
const express = require("express");
const app = express();

$aom.eachRoute(({ method, path, middlewares }) => {
  app[method](path, ...middlewares);
});

app.listen(3000);
```

При этом внутрь соответствующих middlewares будут попадать разные значения. В случае с koa - это `ctx`, который может быть расширен собственными миддлварями сервера, а в случае с express - это `req`, `res`, внутри которых также могут происходить разного рода присвоения и назначения.

Именно для этого и следует понять, как сделать такую настройку, чтобы корректно пробрасывать их внутрь.

Итак, у нас есть некая типовая посадочная функция, которая выглядит несколько по-своему для каждого фреймворка, и из которых по сути нужен достаточно понятный набор значений, причем в режиме readonly. То есть нам надо получить их всего один раз, или, точнее говоря, получать каждый раз одинаковым способом.

И, что характерно, функция установки должна вернуть очень понятную структуру, которая будет однозначно интерпретироваться в непосредственных эндпоинтах. А также следует обозначить функцию возврата контента, который в конечном счете получается внутри контроллеров `aom`.

То есть, предполагается следующая механика:

- должны быть две функции in и out
- in извлекается из входящего контекста релевантные значения и превращает их в типовую структуру, на которую расчитывают декораторы aom
- out возвращает типовую структуру (err, value, next), на которую может соответствующим образом отреагировать сам сервер

При этом их инициация и возврат должны быть синхронизированы друг с другом унифицированным образом. То есть вариант визуализации должен сойтись примерно к такой механике

```ts
$aom.routes.forEach((route) => {
  app[route.method](route.path, async (req, res, next) => {
    try {
      req.body = await route.apply({
        ctx: { req, res },
        next,
        body: req.body,
        query: req.query,
        files: req.files,
        params: req.params,
        headers: req.headers,
        cookies: req.cookies,
        session: req.session,
      });
    } catch (e) {
      req.status = e.status;
      req.body = e;
    }

    return req.body || next;
  });
});
```

То есть мне следует строго типировать только лишь одну конструкцию, которая будет являться основанием для всех последующих вычислений внутри. И исходя из значения этого типа корректным образом пробрасывать её внутрь того, на что будут опираться параметрические декораторы.

Теперь надо понять, как то, чем являются декораторы методов будут использовать то, что является входящим значением, и как это значение можно расширять за счет `state` с `@This` значениями.

## Сборка результата

Прежде чем продолжить писать дальше код декораторов, мне надо фактически сразу написать механизм сборки всего набора контроллеров воедино.

Итак, что это будет?

Прежде всего контроллеры остаются всё теми же классами, которые соединяются между собой за счет `@Bridge` и `@UseNext`. Таким образом всегда есть некий корень, откуда я могу двигаться. То есть чисто технически я могу использовать либо тот же класс `AomHttp`, добавив в него соответствующие методы, либо создать новый, который будет работать исключительно с входящими контроллерами, и пересобирать их согласно тому, как они описаны через `AomHttp`.

Рассмотрим скорее второй случай, чтобы не смешивать всё в кучу. Назовём его `AomAPI`, так как подразумеваем, что оно собирается именно структуру API.

```ts

class AomAPI {

  routes: [];

  constructor (root: Constructor, prefix?:string) {
    const aomHttp = AomHTTP.instance(root);
  }

  private build(root: AomHTTP, prefix = "/") {
    root.endpoints.forEach();
    root.middlewares.forEach();
    root.bridges.forEach();

    this.routes.push(...);
  }
}

```
