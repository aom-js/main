# Ядро `aom`

Ядро `aom` предоставляет механику создания мета-окружения и возможность использования универсальных декораторов, формирующих свой собственный внутренний контекст согласно базовым правилам.

## Что будет уметь данное ядро?

Чтобы получить ответ на этот вопрос, следует двигаться в том числе в обратном направлении. То есть смоделировать такой код, который будет выполнять релевантные требования, которые закладываются в возможности ядра.

Для этого надо также сформулировать те требования, которые предъявляются к будущей механике. Методы ядра будут применяться внутри декораторов, создавая тем самым внутри них сквозные возможности для обогащения релевантных сущностей мета-данными. При этом, весьма вероятно, сами по себе мета-данные даже не будут использоваться, и всё будет построено на Map/Set.

А расшифровка `aom` станет `API over Maps`. Но это неточно.

Однако, вернёмся к сути. Составим несколько примеров того, как по идее может и должен применяться данный подход.

```ts
// при этом при вызове соответствующего метода должна происходить проверка на то, что это статичный метод или свойство
function Endpoint(method: HTTPMethods, path: string = "/") {
  return AomHTTP.methodDecorator(($: AomHTTP) => {
    //
    $.property.meta.handler.define(origin);

    $.target.meta.endpoints.add({ method, path });

    // constructor.checkProperty(origin);
  });
}

//

function Use(...middlewares: MiddlewareHandler[]) {
  return AomHTTP.combinedDecorator(($: AomHTTP) => {
    $.meta.usedMiddlewares.concat(middlewares);
  });
}
```

При этом также, что характерно, должна быть возможность восстановить соответствующий объект из его исходных данных, то есть по комбинации `target` и `property`. Так, что по факту это всё должно храниться синглтоном в мета-свойствах по соответствующим значениям, и извлекаться стандартным набором аргументов.

Далее, следует понять, как лучше всего поступить с теми самыми мета-данными. Чтобы иметь возможность их добавлять, изменять, а также клонировать.

То есть чисто технически соответствующие меты должны быть своими собственными классами, при этом создаваемыми с указанным типом используемых внутри данных, методами которых можно пользоваться стандартным способом.

И вообще в идеале это должно храниться не в мета-данных, а в каком-то собственном системном свойстве, чтобы не надо было каждый раз фиксировать изменения в контексте, если они произошли.

Кстати, хороший вопрос: как это проверить? И можно ли это сделать на WeakMap-ах? Как выясняется, можно, и WeakMap оказываются более подходящими для этой ситуации инструментами, которые и будут использоваться в последующем.

Теперь следует разработать методологию создания соответствующих смысловых конструкций, и превратить их в системную механику.

Для этого следует в первую очередь двигаться от того, чтобы сформировать логику генерации декораторов с использованием соответствующего контекста. Разберем различные примеры, чтобы выявить закономерности, и через это будет понятно, какие должны быть структуры управляющих классов, чтобы они корректно со всем этим добром работали.

Также следует учесть и то, что создаваемые структуры должны уметь удобно разворачиваться в сущности, которые будут применимы для код-генерации.

```ts
// начнем с примера, описывающего создание ендпоинтов

function Endpoint(method: HTTPMethods, path: string = "/") {
  return AOMHttp.methodDecorator(($: AOMHttp) => {
    //
    $.property.meta.handler.define(origin);

    $.target.meta.endpoints.add({ method, path });

    // constructor.checkProperty(origin);
  });
}

// что из этого следует понять, какими свойствами будет обладать сам клас AOMHttp
class AOMHttp extends AOM {
  /*
  за счет наследования он получает возможность создавать свои декораторы, которые уже настроены на контекст самого класса
  от этого надо понять, как унифицированным образом создавать сами базовые методы, чтобы при их создании сразу в контекст 
  прописывать отсылки к текущему обрабатываемомум в контексте свойству и дескриптору, чтобы на них можно было опереться 
  внутри
  */
}
```

## Создание декораторов для свойств, а также обращение через инстансы конкретных экземпляров.

Итак, есть следующие кейпоинты, которые надо корректно разрулить.

1. использование тех же фабрик методов для того, чтобы делать их для собственных методов объектов. При этом следует разрулить кейс связанный с тем, чтобы получать через инициативную функцию декоратора корректный доступ к исходному классу инстанса.
2. использование фабрик для декорирования свойств класса. При этом крайне важно понять, для чего это вообще может применяться, и как это куда-то помещать.

Оба кейса при этом связаны между собой. И вероятно, решать их следует начиная со второго.
То есть у меня есть ситуация, где я имею одновременно target и property, но при этом само релевантное значение не является подходящим для того, чтобы можно было его использовать в качестве ключа при определении инстанса.
Здесь ключевым моментом является то, что при попытке извлечь значение по `Reflect.getOwnPropertyDescriptor` в случае применения `propertyDecorator` либо не определено (для собственных свойств инстанса), либо имеет свойство `enumerable: true` (для статичных свойств), что позволяет его выделить отдельно.

Таким образом формируется требование к тому, чтобы иметь возможность хранить совокупность значений `target`+`property` таким образом, чтобы они создавали свой собственный инстанс того же класса, доступный в дальнейшем для повторного использования. И одновременно с этим необходимо, чтобы для ситуаций, когда используется конкретный хэндлер, являющийся декорированным свойством класса. При этом следует также проверять, что если для данного хэндлера уже есть AomCore-обертка, но впоследствии она инициируется с учетом конкретного класса+свойства, то их между собой надо корректно связать.

То есть здесь надо проверять на то, какие типами являются конструкторы, заходящие в `AomCore.instance`, и от этого принимать решения, как именно состыковывать между собой элементы.

Следовательно, на уровне вызова `instance` надо извлекать информацию о `constructor`, который будет являться основанием для хранения информации о том, какие свойства определены, а значениями для них будут являться инстансы того же класса, в рамках которого происходит оборачивание.
То есть я создаю два свойства в `aomNode`

```
{
  properties: Map<string, T>;

  statics: Map<string, T>;
}
```

Также следует добавить функцию `isClass`, которая будет проверять, что значение `constructor` является классом, для которого эти значения могут быть применены.

Итого, какие следует сделать преобразования?

1. Исправляем работу со свойствами, выполняя проверку на то, что указанное property является собственным методом, и его descriptor.value можно использовать в качестве instanceKey
2. Для свойств, которые не являются методами, и могут не иметь значения descriptor используются две карты `properties` и `statics`, которые позволяют создать требуемый инстанс, и вернуть его. В дальнейшем можно получить доступ к соответствующей декоративной обертке используя имя этого свойства, или перебирая значения в соответствующей карте.
3. Независимо от того, был использован метод для статического или собственного свойства класса, значение `target` равно самому классу, что позволяет в случае взаимодействия с произвольно взятым инстансом получить общую на весь класс обёртку. Возможно эту механику еще потребуется переделать, но пока оставлю так.
