# Руководство по использованию изоляторов

Изоляторы позволяют создавать распределенные сервисы, взаимодействующие через шину сообщений (Kafka, NATS и т.д.).

## Основные концепции

1. **Изоляция и выполнение** - Разделение классов на изолируемые (`@Isolation`) и исполняющие (`@Execution`), что позволяет распределить выполнение методов между разными сервисами.

2. **Топики сообщений** - Методы изолируемых классов преобразуются в топики сообщений, которые могут быть:

   - Без ожидания ответа (`@CustomTopic`)
   - С ожиданием ответа (`@ResponseTopic`)

3. **Идемпотентность** - Поддержка синглтон-режима для предотвращения повторного выполнения одинаковых запросов.

4. **Асинхронное взаимодействие** - Использование RxJS для обработки асинхронных потоков сообщений и ответов.

5. **Конфигурируемость** - Возможность настройки изоляторов под различные шины сообщений (Kafka, NATS) через единый интерфейс.

## Основные декораторы

1. `@Isolation()` - помечает класс как изолируемый
2. `@CustomTopic()` - создает топик без ожидания ответа
3. `@ResponseTopic()` - создает топик с ожиданием ответа
4. `@Execution()` - помечает класс как исполнитель изолированных методов

## Конфигурация

Изоляторы могут быть запущены на различных шинах данных, в том числе в рамках одного проекта. В общем случае может быть установлена конфигурация по умолчанию. Для этого следует установить настройки конфигурации, указав в них способы отправки и подписки на сообщения в топиках, где будет определена механика кодирования/декодирования значений, характерных конкретному инструменту.

Значения `instanceName` и `instanceKey` используются для разделения контекста в запускаемых сервисах, использующих общую шину. Чтобы, если изоляторы повторно инициируются в других инстансах, не было пересечений контекста при отправке сообщений и ожидании ответов.

В настройках подписки используется `next`-функция, в которую передаётся значение, полученное из соответствующего топика.

** Пример для `Kafka` **

```ts
const producer = kafka.producer({
  createPartitioner: Partitioners.LegacyPartitioner,
});
await producer.connect();

// создаем подписчика, который работает в указанном рантайме
const consumer = kafka.consumer({
  groupId: `isolators_${INSTANCE_KEY}_${INSTANCE_NAME}`,
});

await consumer.connect();

Isolator.default({
  //
  instanceKey: INSTANCE_KEY,
  //
  instanceName: INSTANCE_NAME,

  publisher: (topic, message) => {
    const topicMessage = { topic, messages: { value: JSON.stringify(message) } };
    producer.send(topicMessage);
  },

  subscriber: (topic, next) => {
    consumer.subscribe({ topic }).then(() => {
      consumer.run({
        eachMessage: async ({ message }) => {
          // отправим соответствующий результат сообщения
          next(JSON.parse(String(message.value)));
        },
      });
    });
  },
});
```

** Пример для `NATS` **

```ts
// используем стандартное кодирование
const sc = StringCodec();

Isolator.default({
  //
  instanceKey: INSTANCE_KEY,
  //
  instanceName: INSTANCE_NAME,

  publisher: (topic, message) => {
    nats.publish(topic, sc.encode(JSON.stringify(message)));
  },

  subscriber: (topic, next) => {
    nats.subscribe(instanceTopic, {
      callback: (err, message) => {
        next(JSON.parse(sc.decode(message.data)));
      },
    });
  },
});
```

Создание разделенных конфигураций для нескольких шин возможно за счет создания собственных экземпляров класса `Isolator` с последующим их использованием в аргументах декоратора `@Isolation()`. Без указания аргумента используется конфигурация по умолчанию.

```ts
const kafkaIsolator = new Isolator({ instanceKey, instanceName, publisher, subscriber });

const natsIsolator = new Isolator({ instanceKey, instanceName, publisher, subscriber });
```

## Пример базового использования

Изолированный класс по сути представляет собой интерфейс для обращения к релевантной структуре данных, описывая требуемые аргументы и возвращаемые типы. Сама изолированная функция не вызывается.

Исполнение релевантного кода происходит в исполняем классе, который наследует соответствующий изолированный класс, и помечен соответствующим декоратором. Все релевантные настройки для отправки и получения данных из шины класс-исполнитель берёт из настроек родительского изолированного класса.

Исполнителей может быть несколько, где каждый обрабатывает какой-то специфический изолированный метод класса.

Изолируются только статические методы класса.

```ts
// создадим изолированный класс
@Isolation()
export class IsolatedPusher {
  @CustomTopic()
  static async SendMessage(loginId: string, message: MessageData): void {
    //
  }
}

// создадим исполнителя
@Execution()
class PusherExecution {
  static async SendMessage(loginId: string, message: MessageData): void {
    const login = models.Logins.findById(loginId);
    await login.sendMessage(message);
    //
  }
}
```

## Дистрибуция изоляторов

Итак, следует добавить механику описаний свойств изолированных методов для того, чтобы иметь возможность их выгрузить в качестве схемы данных через саму шину данных.

Каким может быть решение?
Скорее всего, здесь будет задействовован некий собственный класс, который встраивается в компоненту `@aom-js/transfer`, и позволяет использовать его как основание для общего пространства для опросов всех активных узлов.

Что-то типа `AomDistributor`, который подключается в контексте дистрибутируемых узлов, и затем используется как общее значение в сервисах, собирающих релевантную информацию у себя.

При этом, что характерно, он же является хранилищем релевантной информации о схемах, в том числе полученных. Что должно позволить в конечном счете сделать условно-независимую систему, которая в случае неактивности какого-то из узлов, "раздающего" изоляторы, будет получать релевантные схемы из других узлов, которые их получили ранее.

Таким образом задачу следует решать в следующем порядке:

1. Создание механизма регистрации распределенных изоляторов через общий на все инстансы класс (являющийся в то же время системным значением).
2. Создание механизма опроса всех сервисов в шине, через тот самый общий системный класс, со сборкой сопутствующей информации о том, какие изоляторы задействованы. Если инстанс, раздающий изоляторы, недоступен, то информация о них может быть получена из других сервисов. При этом для этой информации может быть проведена проверка контрольной суммы структуры данных, и выбрана самая свежая, если значения расходятся.
3. Восстановление структуры изоляторов на основании хранимой схемы с сопутствующим окружением.

Начнём решать задачу именно в таком порядке.

Для этого создадим тестовый стенд, в котором будут 3-4 сервиса, между которыми следует создать механику общения друг с другом.

После того, как у меня объявляются изоляторы, мне надо их каким-то образом "зарегистрировать" в шине. И иметь соответствующую возможность опросить эту самую шину на предмет имеющихся в ней изоляторов.

Допустим, что для этого будет использоваться некий системный класс, который будет являться локальным хранилищем информации о зарегистрированных изоляторах.

Как это может выглядеть на уровне кода?
Итак, у меня есть две ключевые точки в каждом сервисе:

Первая точка - это конфигурация подключения к шине. Внутри которой, по всей видимости и будет находиться настройка регистрационной сущности. Так её и назовём: `Registry`. Ну или можем использовать собственный метод сущности `Transfer`, которая является в данном случае сконфигурированным инстансом.

```ts
import { Transfer } from "@aom-js/transfer";
import { StringCodec } from "nats";

import { default as nats } from "../connections/nats";

const { INSTANCE_NAME, INSTANCE_KEY } = process.env;

// используем стандартное кодирование
const sc = StringCodec();

// настроим изолятор по умолчанию
export default new Transfer({
  //
  instanceKey: INSTANCE_KEY,
  //
  instanceName: INSTANCE_NAME,

  publisher: (topic, message) => {
    nats.publish(topic, sc.encode(JSON.stringify(message)));
  },

  subscriber: (topic, next) => {
    nats.subscribe(topic, {
      callback: (err, message) => {
        return next(JSON.parse(sc.decode(message.data)));
      },
    });
  },
});
```

Вторая точка - это создание каждого изолятора. Здесь, полагаю, имеет смысл использовать ту самую регистрацию. При этом надо также понять, будет ли регистрировать каждый общий метод отдельно, или будет регистрировать весь класс.

Допустим это будет выглядеть так: если стоит метод на классе, то регистрируется целиком, а если на отдельном методе, то соответственно только этот метод. Ну или поскольку для методов надо так или иначе указывать параметры и их типы, а также возвращаемые значения, то их определение будет являться тем признаком, что с такими типами и будет фиксироваться информация о конкретном методе и его параметрах.

```ts
import { Isolator, CustomTopic, ResponseTopic } from "@aom-js/transfer";

import transfer from "@/config/aom/transfer";
import * as entities from "@/entities";

@Isolator(transfer)
@transfer.Register()
export class PusherIsolator {
  @CustomTopic()
  static async SendMessage(mailingId: string): Promise<void> {}

  @ResponseTopic()
  static async RegisterMessage(
    loginId: string,
    message: IEmailMessage
  ): Promise<entities.Mailings> {
    return;
  }
}
```

Как при этом будет использоваться та информация, которая помещена в реестр? Её можно получить, опросив шину, и получив соответствующий список в подписочном методе.

То есть эта конструкция должна иметь своего исполнителя, данные в котором будут регистрироваться и фиксироваться в качестве локальных значений. Собственно, этим подписчиком будет являться та процедура, которая будет собирать эти самые изоляторы и фиксировать их локально. При этом, что характерно каждый создаваемый инстанс должен иметь свою собственную автоматически инициируемую процедуру подписки, работающую всегда в момент запуска сервиса.

И она же являющейся автоматической отвечалкой на поступающие запросы.

То есть её надо делать стандартной парой "изолятор/исполнитель", с уже настроенными значениями. И при этом не зарегистрированными в самой шине, так как нет в этом никакой нужды.

Как это может быть организовано?

Допустим для этого будет использован тот принцип класса TransferRegistry, который занимается той самой полезной нагрузкой.

При этом, по всей видимости, так как часть логики будет происходить за счет того, что будет использоваться `extends` от некоего стандартного класса, то надо будет добавлять механику переноса свойств по аналогии, с кем, как это использовалось на контроллерах. Но на самом деле не критично, потому что я могу себе это быстро позволить. Здесь по большей части стоит вопрос, на какой из топиков будет происходить в этом случае подписка.

Так-с, из хорошего: если изоляторы имеют одинаковые имена, то они соответственно одинаково подписываются на релевантные топики и получают запрос все вместе. То есть, зная наверняка, что есть некое общее пространство имён, можно планировать механику запросов и ответов. При этом для того, чтобы ответ получил нужный инстанс, он должен в своём запросе представляться, и соответственно последующий ответ должен быть направлен в нужный инстанс.

При этом, как видно, создаётся и задача другого рода: использование статичных методов для хранения и обработки топиков становится скорее недостатком, который следует исправить.

Чисто технически нет особой проблемы с тем, чтобы перевести всё на собственные методы. Включая в том числе последующие ограничители выполнения очередей. Это, возможно, будет наиболее правильным выходом.
Таким образом, что топики будут формироваться исходя из собственного имени класса, а их вызов будет происходить за счет команды типа `const result = await new Isolator().method(...args)`.

Причём, здесь, по всей видимости, я смогу решить и задачу вида указания специфического инстанса, куда при необходимости надо отправлять ответные сообщения. То есть за счет `await new Isolator(instanceName).method(...)` я смогу позволить себе регулировать эту процедуру корректным образом. Таким образом, что и создание исполнителей будет происходить с указанием того имени инстанса, в котором они будут слушать свои подписки. Что, судя по всему, корректно решает мой кейс.

Однако это немного не решает той задачи, где мне надо создавать унифицированный изолятор, который уже будет подключен к соответствующему трансферу и реагирует одинаково на все вызовы в нём.

В общем, надо подумать, как это в целом может решаться.

Есть мнение, что эта механика должна быть собственной частью самого класса Transfer. То есть он сам по себе делает подписку на общий топик, и сам же является хранилищем регистрационной информации.

То есть на уровне самого конструктора Transfer создается служебный топик, который занимается исключительно тем, что создает стандартную процедуру subscribe/reply, и в целом позволяет также внутрь себя подключить некую процедуру "слушания", которая будет вызывать опрос шины, и получать полезную информацию.

Тут, впрочем, есть тонкий момент связанный с циклическими зависимостями. Когда один сервис, предоставляющий кому-то свои изоляторы, сам по себе требует наличия в себе изоляторов из другого места. И в этом случае разумным решением становится кейс, где я всё-таки храню внешние изоляторы внутри локального репозитория, при необходимости их обновляя скриптом. Это также избавит меня от необходимости иметь свой собственный диспетчерский сервис, который будет раздавать недостающие звенья. Однако на деле он всё-таки оказывается необходимым. При этом его особенностью должно быть в том числе хранение и "сырых" структур об изоляторах. Таким образом, что в целом механика включения нового сервиса будет происходить с того, что будет вызывать некий `register` скрипт, который без запуска непосредственно ключевого кода соберет информацию обо всех используемых изоляторах, и зафиксирует их в диспетчерской службе.

В общем, ситуация со всех сторон нетривиальная, и будем, опять-таки, решать её последовательно.

К слову, мне также надо сделать возможность использовать очереди для контроля массовости получения сообщений в случае распределенных узлов, выполняющих одну и ту же задачу.

Полагаю, на самом деле надо начать именно с неё. Для этого следует в subscriber внедрить параметр, определяющий признак того, что данная подписка является очередью. И это делается за счет использования декоратора `@IsQueue()`, который передается в качестве аргумента в subscriberHandler-функцию, и учитывается при инициации функции в соответствующем конфиге класса. И это работает.

Теперь следует решить задачу с общими сквозными топиками в шине, где будет происходить соответствующая механика массовых оповещений.

Для этого следует расписать конечное представление того, как это будет храниться, собираться и распространяться. И также сделать вывод о том, а имеет ли смысл продолжать использовать изоляторы как контейнеры с исключительно статичными методами, и перевести всё-таки эту механику на то, чтобы они были собственными свойствами.

Полагаю, имеет смысл начать именно с этого, потому что напрашивается то, что общий в шине изолятор должен быть классом, который хранится во внутренней коллекции библиотеки `transfer`, и подключаться автоматически, функционируя по тому же принципу, что и остальные создаваемые изоляторы.

Альтернативой этому может быть использование стандартных механик на встроенных функциях, которые уже обеспечивают нужный функционал. И именно от него я буду отталкиваться, и потом, если что, перейду на альтернативную версию. Потому что на самом деле надо начать с того, как в целом будет происходить тот самый процесс системных регистраций и оповещений.

Итак, у нас есть некий класс `Transfer`, экземпляр которого создается в каждом сервисе, и который является той самой общей составляющей, на которую "цепляются" все изоляторы.

Далее, допускаем, что у изоляторов есть дополнительный декоратор, характеризующий их как "распределенный", то есть доступный в других сервисах. При этом, что характерно, по хорошему надо бы сделать защиту от того, чтобы в разных сервисах использовались одинаковые по названиям изоляторы, от которых наследуются различные исполнители. Но это, видимо, будет второй частью модификации.

Итак, расписываем задачу по шагам:
шаг №1 - зафиксировать в шине информацию о том, что появился новый изолятор. Это делается, наприме, за счет использования декоратора `@Distributed()`, который имеет время запуска `LAST`, и в контексте значения `$.transfer` выполняет фиксацию в какой-либо Map своего значения по `$._.target`.

шаг №2 - сообщить о том, какие изоляторы доступны. Вот тут-то начинается самое интересное, потому что процедура этого действия будет состоять в следующем:

- имеется несколько сервисов А, В и С. Каждый из них имеет набор изоляторов, которые он распространяет, например А1, А2, В1, В2, В3 и С1. Каждый из них в той или иной форме зафиксирован в контексте имеющегося transfer, к которому подключены остальные сервисы.
- сервис А делает запрос о доступности изоляторов в других сервисах, указывая, какой именно сервис запрашивает, то есть передавая свои INSTANCE_NAME и INSTANCE_ID значения
- в подписчиках всех сервисов проверяется, что если указанные значения INSTANCE_NAME и INSTANCE_ID не совпадают с собственными, то они кидают в шину с указанием INSTANCE_NAME и INSTANCE_ID свою информацию о том, какие изоляторы они хранят
- в соответстующем сервисе проверяется, что если указаны его INSTANCE_NAME и INSTANCE_ID, то он принимает получаемую информацию и обрабатывает её корректным образом

Таким образом создается два системных топика: `isolators_request` и `isolators_response`, у которых должна быть стандартная реакция, чисто технически полностью совместимая с имеющимися процедурами публикации.

То есть получается следующее

```ts
class Transfer {
  constructor() {
    // ...

    // подписаться на топик, в ответ на который будет отправлен состав имеющихся схем
    this.subscriber({
      topic: this.registryRequestTopic,
      next: (message) => this.requestRegistry(message.value),
    });

    this.subscriber({
      topic: this.registryResponseTopic,
      next: (message) => this.acceptRegistry(message.value),
    });
  }

  collectDistributions(colllectCallbackHandler: StructureCollectorFunction) {
    // зафиксируем функцию получатель
    this.structureCollector = colllectCallbackHandler;
    // соберем информацию о текущем инстанса
    const { instanceName, instanceKey } = this;
    const value = { instanceName, instanceKey };
    //  опубликуем от текущей ноды запрос в о структурах в общем реестре
    this.publisher({
      topic: this.registryRequestTopic,
      message: { value, headers: {} },
    });
  }

  private requestRegistry(sender: InstancesData) {
    const { instanceName, instanceKey } = this;
    if (!(sender.instanceName === instanceName && sender.instanceKey === instanceKey)) {
      const schemas = this.registryMap.entries();
      const value = { receiver: sender, sender: { instanceName, instanceKey }, schemas };
      this.publisher({ topic: this.registryResponseTopic, message: { value, headers: {} } });
    }
  }

  private acceptRegistry(registry: TransferRegisty) {
    const { receiver } = registry;
    const { instanceName, instanceKey } = this;
    if (
      this.structureCollector &&
      receiver.instanceName === instanceName &&
      receiver.instanceKey === instanceKey
    ) {
      const { schemas, sender } = registry;
      // тут сформируем структуру для её обработки в функции получения данных из реестра
      const structureData: StructureReceiveSchema = { instance: sender, value: schemas };
      // и вызовем сборщик структур, передав релевантную информацию
      Reflect.apply(this.structureCollector, null, [structureData]);
    }
  }
}
```

Таким образом осуществляется механика запроса и получения всех данных из активных шин.

Теперь следует сделать, собственно говоря, те самые значения, которые будут сохраняться, передаваться и восстаналиваться.

Судя по всему, требуемым результатом будет некая гибридная схема, похожая на openapi, но со своими нюансами.

Что в общем случае следует в ней учесть?

Она скорее всего будет похожа на ту, что предложил chatgpt

Как бы там ни было, следует предугадать, каким будет конечная визуализация, чтобы это заработало.

Возьмем типичный изолятор, который уже использует своё собственное окружение.
По сути своих модификаций он сводится примерно к тому же, что я делаю в контексте `@aom-js/api`. То есть в данном случае для каждого аргумента должен быть добавлен свой декоратор с определением типа, а для самого метода должен быть добавлен декоратор с возвращаемым значением.

Итак, концептуально мне требуется механика уровня `jsonschema<->typescript`, которая при этом должна стать нативной частью функционала `ComponentSchema`, чтобы при этом поддерживать каскадное составление типов, включенных внутрь соответствующих `$ref`-конструкций. Потому что без них никуда.

То есть, если подразумеваем преобразования первого уровня, то на "входе" имеет стандартные классы, обрисованные декораторами семейства `class-validator`, которые позволят получить из них релевантное jsonschema-значение, которое можно будет обратно восстановить, используя подходящую библиотеку.

При этом, что важно, полученное значение в jsonschema надо сохранить таким образом, чтобы его можно было использовать в openapi-схеме. То есть учитывающие механику гибридных вызовов рендереров из `@aom-js/schemer`.

Для того, чтобы понять предсказуемость совершаемых действий, необходимо подобрать соответствующие библиотеки для преобразований.

## Изолятор в инстансах

Супер важной задачей на модификацию всей логики изоляторов является требование убрать статичные методы, и поместить все вызовы в инстансы.

Для чего это нужно?

Во-первых, это позволит убрать async-ожидание установки конфигурации, которую впоследствии надо будет прокидывать в каждый изолятор.

Вроде бы как-будто с этим можно даже смириться, так как изоляторов в принципе не так много, но напрашивается механика, где изоляторы могут вызываться с аргументом, определяющим их инстанс в момент вызова, что полностью нивелирует все возможные проблемы с перехлёстом идентификаторов.

### Как можно решить данную задачу?

Для начала определим визуальную форму описания этих данных. То есть оно будет выглядеть как

```ts
@Controller()
class SomeClass {
  //
  static async SomeMethod() {
    new Isolator({ userId, token, wtf }).startExecution(param1, param2);
  }
}
```

Таким образом, что внутри исполнителя можно точно также использовать прием этих значений, и делать какие-то проверки валидности контекста и возможностей. Здесь, правда, формируется сложность второго порядка, что их применение будет по большому счету асинхронной функцией, собирающей данные из разных источников, и тем самым ограничивающую механику использования этих самых данных.

А также не позволит делать исполнителей внутри контроллеров, что применимо для тех же сокетов.

Так что не исключено, что корректно будет оставить эту логику как есть, а если требуется собрать какой-то специализированный контекст, то использовать для этого аргументы метода изолятора, которые обеспечат требуемую совместимость с асинхронностью и смежной сложностью.
