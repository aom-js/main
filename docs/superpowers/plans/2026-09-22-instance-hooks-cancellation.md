## Суть

Хуки `@OnInstance` одного и того же класса запускаются параллельно (`Promise.all` по `instanceHooks` в `AomApi.instanceWithHooks`). Отказ одного хука не отменяет уже запущенные соседние: их побочные эффекты выполняются и после того, как клиент получил `401`.

## Как это выглядит

```ts
@Controller()
class Session {
  // проверка: отказывает быстро
  @OnInstance()
  static async verify(@Headers("authorization") auth: string) {
    if (!auth) throw new AuthRequiredResponse("no token");
  }

  // соседний хук: медленный и с последствиями
  @OnInstance()
  static async touch(@This() self: Session) {
    await db.sessions.update({ lastSeen: new Date() });
  }
}
```

`verify` отказывает, запрос завершается `401` — а `touch` к этому моменту уже запущен и доводит запись в базу до конца. То же касается любого хука, который пишет в журнал, ставит задачу в очередь или трогает внешний сервис.

Риск утечки непроверенного объекта чужому коду здесь уже снят (`KI-ROUTER-16`): до окончания всех хуков инстанс виден только собственному коду класса. Остаётся именно незавершаемость побочных эффектов.

## Почему переход на последовательный запуск отложен

1. **Время.** Сейчас стоимость проверок — максимум по хукам, при последовательном запуске станет суммой. Для класса с двумя-тремя обращениями к базе это заметно на каждом запросе.
2. **Ловушка порядка при наследовании.** Собственные декораторы метода потомка отрабатывают раньше, чем `@Controller()`, который запускает `inherit()` и добавляет хук родителя в `instanceHooks` последним (`OnInstance` — `$._.root.element.instanceHooks.push($)`). То есть унаследованная проверка родителя может оказаться в очереди последней — и при последовательном запуске она будет выполняться после собственных хуков потомка, что для проверки доступа ровно наоборот тому, что ожидается.

Пока хуки идут параллельно, порядок ни на что не влияет и ловушка не видна. Как только порядок станет значимым, её придётся решать в той же задаче.

## Что нужно сделать в этой задаче

- [ ] Решить, что именно нужно: последовательный запуск, отмена соседей при отказе (`AbortSignal` в хуки) или разделение хуков на «проверки» и «эффекты» с разными правилами.
- [ ] Разобраться с порядком при наследовании: должна ли унаследованная проверка родителя идти первой, и если да — менять порядок регистрации в `inherit()`/`OnInstance` или сортировать `instanceHooks` перед запуском.
- [ ] Измерить цену на реальном приложении: сколько хуков на классе, сколько каждый занимает, во что превращается сумма вместо максимума.
- [ ] Закрепить выбранное поведение тестами: отказ проверки должен останавливать соседний хук с побочным эффектом (или явно не останавливать, если решение — оставить как есть и задокументировать).
- [ ] Описать правило в `docs/cookbook`: что можно делать в хуке экземпляра, а что нельзя, пока отмены нет.
