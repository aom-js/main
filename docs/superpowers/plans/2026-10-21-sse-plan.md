# SSE в ядре — план

Задача `aom-main-ann`. Заготовка — пустой `packages/api/src/controllers/events/sse.ts`. Принцип — как у WebSocket-точек (`packages/api/readme.md`, раздел «WebSocket-точки»): реестр соединений по id приложения, `send`/`broadcast`, доставка из других процессов через изолятор. Отличие: SSE — обычный HTTP GET, поэтому ссылка живёт в общем дереве маршрутов, проходит гейты и попадает в OpenAPI.

Коротко: SSE-ссылка — обычный `@Get`, который возвращает поток из реестра `AomServerEvents`; описывается в OpenAPI через `@Responses` с новой опцией `events`; отправка — методы реестра, из других процессов — изолятор с `@CustomTopic()`.

## 1. Чем будет SSE-ссылка

| | A. Свой декоратор `@ServerEventsPoint` (как `@WebSocketPoint`) | B. `@Get` + реестр `AomServerEvents` |
|---|---|---|
| Роутер | новый флаг, свой список маршрутов, своя ветка в `Server` | без изменений |
| Гейты, `@Before`, `@This` | повторять отдельно | работают как у любого GET |
| OpenAPI и manifests | выпадают, как сокеты (`KI-ROUTER-06`) | попадают сами |
| `Server` | новая ветка | уже стримит `Readable` через `Stream.pipeline` (`packages/api/src/server/http.ts` (`Server`)) |
| Принцип владельца «расширение — опцией» | новый декоратор | опция |

**Выбор — B.** Middleware-контроллер по образцу `WebSocketsController.Define/Connect` не нужен: у `upgrade` нет обычного ответа, а у GET есть; id известен в самом обработчике, поэтому порядко-зависимой связки `@Before(Define)`/`@After(Connect)` нет.

```ts
// псевдокод: пример в приложении
@Controller()
@Executor()
export class MyPermissionsEvents extends PermissionsEventsIsolator {
  static events = new AomServerEvents({ unread: UnreadEvent }); // имя события -> класс @ComponentSchema

  static async TotalUnread(data: UnreadEvent, orgUserId?: string) {
    orgUserId ? this.events.send(orgUserId, "unread", data) : this.events.broadcast("unread", data);
  }

  @Get("/events")
  @Responses(MyPermissionsEvents.events.JSONSchema("Счётчик непрочитанного"))
  static Connect(@This(CurrentOrg) { orgUser }: CurrentOrg, @Ctx() { res }: HttpCtx) {
    return this.events.connect(orgUser.id, res); // PassThrough -> Server пайпит его в res
  }
}
```

`connect(id, res)`:
1. ставит заголовки `setHeader`: `Content-Type: text/event-stream; charset=utf-8`, `Cache-Control: no-cache`, `Connection: keep-alive`, `X-Accel-Buffering: no` (`Server` свой тип не подставляет, если тип уже задан);
2. создаёт `PassThrough` и кладёт первый кадр (`retry: N` или `: connected`) — заголовки уходят сразу, у клиента срабатывает `onopen`;
3. регистрирует поток под `id`, ставит heartbeat;
4. по `close` снимает поток с реестра (уход клиента — `pipeline` сам разрушает источник);
5. возвращает поток.

Клиент — fetch-клиент SSE с обычными заголовками (например, `@microsoft/fetch-event-source`): `fetchEventSource(url, { headers: { authorization, "data-org-id": orgId }, onmessage: (e) => e.event === "unread" && JSON.parse(e.data) })` // псевдокод

## 2. Описание по схемам

- Роутер генерирует OpenAPI **3.2.0** (`OpenApi.version`, типы `openapi3-ts/oas32`, стадия 0): у Media Type есть стандартное поле `itemSchema` — схема одного элемента потока, для `text/event-stream` — одного события. Swagger UI — `swagger-ui-dist@5.33.1`, документы 3.2 он рисует.
- `@Responses({ contentType: "text/event-stream" })` работает уже сейчас (`packages/router/src/common/openapi.ts` (`OpenApiResponse`), `packages/router/src/classes/openapi.ts` (`OpenApi.registerPath`)). Не хватает типизированных событий.
- `SchemasCollector.extract` не обходит классы, вложенные в обычный объект, — роутер сам вызывает извлечение схемы для каждого класса события.

### Как меняется `@Responses`

Сейчас (`packages/router/src/common/openapi.ts` (`OpenApiResponse`), `packages/router/src/classes/openapi.ts` (`OpenApi.registerPath`)): ответ — `{ status, schema, description, contentType?, isArray? }`; `registerPath` пишет `responses[status] = { description, content: { [contentType ?? "application/json"]: { schema } } }`, `isArray` оборачивает схему в массив, одинаковый `status` из более позднего курсора заменяет ответ целиком.

**Тип — два вида ответа вместо одного** (декоратор `@Responses(...schemas)` и его накопление в `$.openApi.responses` не меняются):

```ts
// псевдокод: packages/router/src/common/openapi.ts
interface OpenApiResponseBase { status: number; description: string; contentType?: string }
/** обычный ответ — как сейчас */
interface OpenApiDataResponse extends OpenApiResponseBase { schema: OpenApiPossibleSchema; isArray?: boolean; events?: never }
/** поток событий: имя события -> схема его data (класс @ComponentSchema, сырая схема, ThisRef/RouteRef) */
interface OpenApiEventsResponse extends OpenApiResponseBase { events: Record<string, OpenApiPossibleSchema>; schema?: never; isArray?: never }
export type OpenApiResponse = OpenApiDataResponse | OpenApiEventsResponse;
```

`schema` и `events` взаимоисключающие уже в типах: потоку не нужна схема тела, массиву событий нет смысла.

**Сборка в `registerPath`** — одна ветка `if ("events" in response)`:

1. `contentType` по умолчанию — `text/event-stream` (вместо `application/json`).
2. Для каждого `[name, schema]` из `events` — `this.schemaExtract(schema, cursor)`, тот же путь, что у `schema` обычного ответа: класс попадает в `components.schemas` и даёт `$ref`, `ThisRef`/`RouteRef` разрешаются на курсоре маршрута.
3. Пишется media type:

```jsonc
// псевдокод: responses[status].content["text/event-stream"]
{
  "schema": { "type": "string" },          // тело ответа — текст потока
  "itemSchema": { "oneOf": [                    // по варианту на событие
    { "type": "object", "required": ["event", "data"],
      "properties": {
        "event": { "const": "unread" },
        "data":  { "type": "string", "contentMediaType": "application/json",
                   "contentSchema": { "$ref": "#/components/schemas/UnreadEvent" } },
        "id":    { "type": "string" },
        "retry": { "type": "integer" } } }
  ] }
}
```

4. Ключ — стандартное `itemSchema` OpenAPI 3.2 (стадия 0). Приложение его не видит: оно пишет только `events`.
5. Имя события с `\r`/`\n` — ошибка при построении маршрута (иначе кадр `event:` сломается); пустой `events` — тоже ошибка.
6. Слияние по `status` — как сейчас: позднее объявление того же статуса заменяет ответ целиком (поток и JSON на одном статусе не смешиваются).

**Фабрика ответа в api** — по образцу `ResponseJSONSchema.JSONSchema` (`packages/api/src/schemas/json-schema.ts`): `AomServerEvents.JSONSchema(description, status = 200)` возвращает `{ status, description, events: this.schemas }`. Словарь `this.schemas` — тот же, что типизирует `send(id, event, data)`, поэтому схема в документе и типы отправки не расходятся.

**Кто ещё читает ответы:**
- визуализатор (`packages/visualizer/src/defines/graph.ts` (`buildVisualGraph`)) берёт схему ответа из `content[*].schema` — у потока там `{ type: "string" }`; ссылки на классы событий брать из `itemSchema.oneOf[*].properties.data.contentSchema.$ref`, иначе ребро «маршрут → схема события» потеряется;
- `responseJsonSchema` (`packages/api/src/functions/json-schema.ts`) и `ResponseJSONSchema` строят только обычные ответы — не меняются.

**Тесты роутера** (`packages/router/test/openapi.test.ts`): поток с двумя событиями → `schema: {type: "string"}`, `oneOf` из двух вариантов с `contentSchema.$ref`, оба класса в `components.schemas`; `ThisRef` в `events` разрешается на наследнике; имя события с переводом строки и пустой `events` — ошибка; обычный ответ без `events` — байт в байт как раньше; ключ — `itemSchema`.

## 3. Процедура отправки

Реестр — `packages/api/src/controllers/events/sse.ts` (`AomServerEvents`), экспорт — строкой в `packages/api/src/controllers/events/index.ts`.

```ts
// псевдокод
class AomServerEvents<E extends Record<string, ClassType>> {
  connections: Map<string, PassThrough[]>;
  constructor(schemas: E, options?: { heartbeat?: number /* мс, по умолчанию 25000, 0 = выкл */; retry?: number });
  connect(id: string, res: ServerResponse): PassThrough;
  disconnect(id: string, stream: PassThrough): this; // пустой список удаляет ключ
  send<K extends keyof E>(id: string, event: K, data: InstanceType<E[K]>, eventId?: string): void;
  broadcast<K extends keyof E>(event: K, data: InstanceType<E[K]>, eventId?: string): void;
  JSONSchema(description: string, status?: number): OpenApiResponse;
}
```

**Кадр** (функция `formatServerEvent`): `event: <имя>` (перевод строки в имени — ошибка), `id: <eventId>` если задан (то же правило), `data: <JSON.stringify(data)>` построчно — каждая строка по `/\r\n|\r|\n/` со своим префиксом `data: `, пустая строка в конце.

**Служебное:** `retry: <мс>` — один раз в первом кадре; heartbeat `: ping\n\n` по `setInterval(...).unref()` на соединение, снимается по `close` (против обрыва простаивающего соединения прокси: у nginx `proxy_read_timeout` 60 с).

**Правка в `Server`:** при уходе клиента `pipeline` вернёт `ERR_STREAM_PREMATURE_CLOSE`, и `Server` пишет `console.error("Stream error:")` (это касается и оборванных скачиваний). Глушить именно этот случай:

```ts
// псевдокод
if (streamErr.code === "ERR_STREAM_PREMATURE_CLOSE" && res.destroyed) return; // клиент сам закрыл соединение
```

**Из других процессов** — как у сокетов: изолятор `@Isolator(transfer)` с методом `@CustomTopic()` (без `@IsQueue` — доставка всем экземплярам; без склейки `@CustomTopic(true)`), контроллер ссылки — `@Executor()` этого изолятора; отправитель вызывает метод изолятора, каждый экземпляр шлёт своим соединениям. `@aom-js/transfer` не меняется.

**`Last-Event-ID`:** буфера повторной доставки нет; `eventId` передаётся как есть, приложение при переподключении дочитывает пропущенное само (заголовок — через `@Headers`).

## 4. Ограничения и особенности

- Соединения живут в памяти процесса — поэтому доставка через широковещательный топик, не через очередь.
- Браузер по HTTP/1.1 держит ~6 соединений на домен на все вкладки: одна SSE-ссылка на клиентское приложение (типы различаются `event:`), на прокси — HTTP/2 к клиенту.
- Авторизация: `EventSource` не умеет заголовки, а в приложении на заголовках и токен (`AuthHeaderToken`), и организация (`data-org-id`).

  | Способ | Плюсы | Минусы |
  |---|---|---|
  | cookie (`AuthCookieToken` уже есть) | нет утечки в URL | кросс-доменно не работает: `Server` отдаёт `Access-Control-Allow-Origin: *`, с `withCredentials` браузер его отвергает; только тот же origin (через прокси) |
  | токен в query | просто | попадает в логи прокси и историю; нужен короткоживущий одноразовый токен |
  | fetch-клиент SSE (например, `@microsoft/fetch-event-source`) | обычные заголовки, гейты без изменений | зависимость на клиенте |

  Решение владельца 2026-10-21: клиент SSE — fetch-клиент с заголовками (обязателен), гейты и `data-org-id` работают без изменений; `EventSource` не поддерживается. Для WebSocket этот путь закрыт (браузер не даёт заголовков рукопожатию ни в одной библиотеке) — пересмотр передачи токена и организации для всех протоколов — долг в реестре `test/docs/shortcuts.md`.
- Права проверяются один раз, при подключении: отозванный доступ живёт до переподключения.
- Таймауты Node: `requestTimeout` касается приёма запроса (GET без тела принят сразу), `server.timeout` по умолчанию 0, `keepAliveTimeout` — после конца ответа. Проверить тестом стадии 2.
- `server.close()` ждёт открытые SSE-соединения — в тестах и при остановке `closeAllConnections()`.
- Медленный клиент: `PassThrough` копит данные без предела — в коде `shortcut:` с записью реестра.

## Вне плана

Буфер и повторная доставка по `Last-Event-ID`; предел буфера медленного клиента; закрытие всех потоков при остановке процесса; CORS с конкретным origin; перепроверка прав на живом потоке; перевод сокетов приложения на SSE.
