# Выгрузка цепочек маршрутов и общие правила — в ядро

Дата: 2026-10-23. Статус: на утверждении владельца.

## Зачем

Описание цепочек маршрутов и проверки их формы сейчас живут в приложении `test`
(`test/src/lib/manifest/*`, тесты-свойства рядом). Ядро отдаёт только сырую проекцию
(`Router.toJSON`, `AomRoute.toJSON`, `AomCursor.toJSON`). Следующее приложение на ядре
повторило бы тот же код, и копии разошлись бы.

Задача ядра — **выгрузить всё, что характеризует маршрут, в одном готовом виде** и дать
**правила, одинаковые для любого приложения**. Приложение не повторяет процедуру, а
вызывает готовое.

Это часть подготовки документации ядра: по ней потом пишется гайдбук агентской разработки
на демонстрационном коде (`test`). Поэтому результат — не только код, но и раздел в
документации ядра, где агент найдёт, что брать готовым и что дописать самому.

## Решения владельца (этот разговор)

1. **Ядро выгружает факты, приложение решает и проверяет.** Ядро выгружает только факты о
   цепочке: место шага, точка прикрепления, родитель, параметры с их целями (`@This(S)`,
   `@State(S)` — уже есть в `AomCursorJSON.parameters`), объявленный `@CursorKind`, вид,
   выведенный из классов самого ядра, и дамп. **Что чем считается — решение приложения**:
   какие классы — контейнеры данных (вид Transport), какой шаг пишет и какой читает
   (`writtenBy`/`readBy`), какие виды не пишут (сейчас в `test`: Handler, Collector, Value),
   оговорки вроде «Value на копии не читатель» (shortcut KI-TEST-06). Всё это остаётся в
   приложении. Решение №14 спеки метаданных
   (`test/specs/2026-10-11-cursor-metadata-design.md`: «правила вывода, свойства, дамп — на
   стороне приложения») пересмотрено только в части фактов, общих правил и дампа.
2. **Правила, одинаковые для всех приложений, — в ядре** готовыми функциями:
   - один эндпоинт — один маршрут (P1);
   - ident точки доступа уникален в роутере (P2);
   - роутер сериализуется без ошибок, нет неразрешимых ссылок (P7);
   - нет `ThisRef` и `@This()` без аргумента в конструкторах классов маршрута (P8);
   - повтор шага допустим только в оговорённых случаях (P6, правило без остатка; «пишет ли
     шаг» и «какие виды безвредны при повторе» правило получает от приложения параметрами);
   - дамп совпадает с кодом (P9, механизм).

   Номера — по `test/docs/testing.md#свойства-цепочки`.
3. **Архетипы — в приложении.** Грамматики (`archetypes.ts`: список, карточка, создание,
   мутация) и всё, что на них опирается, остаются в приложении.
4. **Правила с данными приложения — в приложении.** «Писатель раньше читателя» (P3), «гейт
   раньше данных» (P4), «параметр пути закрыт» (P5): ядро отдаёт для них факты (цели
   параметров, родители, вид шага), а толкование (кто пишет, кто читает) и проверку с
   порогами, списками публичных маршрутов и остатками пишет приложение.
5. **Пороги, остатки и храповики — в приложении.** Ядро даёт функции «роутер → список
   нарушений» без `expect`; тест с порогом «поиск жив» и остатком пишет приложение.
6. **Место описания — документация ядра о тестировании** (`main/docs`), как часть
   тестирования. Документ для агента: что взять из ядра, что приложение передаёт, что
   пишет само.

## Цели

- Приложение получает обогащённую выгрузку роутера одним вызовом: шаги с видом и родителем
  поверх проекции ядра; текст дампа в постоянном формате.
- Общие правила (п. 2) — готовые функции ядра, возвращают список нарушений.
- `test` переходит на функции ядра; его копии удаляются. В `test/src/lib/manifest` остаётся
  только своё: список модулей, загрузчик роутера, базы контейнеров, архетипы.
- Документ ядра о тестировании описывает выгрузку, правила и границу «ядро / приложение».
  `test/docs/testing.md` в разделе свойств ссылается на него и описывает только своё.

## Не цели

- Архетипы, пороги, остатки, списки публичных маршрутов — не в ядре.
- Проверки P3/P4/P5 — не в ядре (только данные для них).
- Гайдбук агентской разработки — следующий этап, не этот.
- Хелперы уровня приложения (`fixtures`, `executors`, `bus`, тела обхода `sweep`) — не трогаем.

## Анти-цели (провал, даже если работает)

- Ядро импортирует классы приложения (`ShellsBase`, `EntityController` и т. п.).
- Функции ядра вызывают `expect` или зависят от bun:test / vitest.
- Дамп `test/manifests/*.json` меняется без причины, видимой в диффе (перестановка полей,
  потеря поля).
- В приложении остаётся вторая копия правила, которое ушло в ядро.
- Документ ядра ссылается на спеки, планы или задачи трекера (docs замкнуты на docs и код).
- Ядро зашивает толкование одного приложения: список «не писателей», смысл вида шире словаря,
  исключения вроде KI-TEST-06.

## Ограничения

- **Направление зависимостей.** `@aom-js/router` зависит только от core и schemer;
  `@aom-js/api` зависит от router. Вывод видов Checkpoint (`BaseAccessController`) и Input
  (билдеры, `IDController`), правило P2 (маркеры доступа) требуют классов api. Значит,
  выгрузка с видами и правила, которым нужен api, живут в api — подпуть
  `@aom-js/api/testing` по образцу `@aom-js/router/testing` (`package.src.json` exports,
  алиас в `vitest.config.ts`, `scripts/smoke.js`, сборка). То, что не требует api
  (`parentsOf`, P1, P7, P8), может жить в `@aom-js/router/testing`.
- **Раннеры.** Ядро — vitest, `test` — bun:test. Функции ядра чистые, без `import.meta.dir`,
  `Bun.*`, `mock.module`. Файловые операции дампа — через `node:fs`.
- **Приложение исполняет dist.** После правки ядра — `bun run build`; страж «dist устарел»
  в `test/test/helpers/setup.ts` это ловит.
- **Аддитивность.** Существующий API ядра не меняется; `AomCursorJSON` остаётся как есть.

## Что передаёт приложение

- **Свой вывод вида** для классов приложения (у `test` — наследники `ShellsBase` → Transport):
  функцией или списком баз; ядро применяет его после `@CursorKind` и до своих правил. Без
  него ядро выводит виды только из своих классов.
- **Толкование для P6**: предикат «шаг пишет» и виды, повтор которых безвреден (у `test` —
  Transport, Checkpoint). `writtenBy`/`readBy` и список «не писателей» остаются функциями
  приложения.
- **Служебный маршрут** (`isService` для P4) — толкование, остаётся в приложении.
- **Роутеры и место дампа**: какие роутеры выгружать и куда класть файлы.

Вид, который нельзя вывести, приложение помечает `@CursorKind` на определении шага, как и
сейчас.

## Что остаётся решить исполнителю

- Точные имена и сигнатуры функций; форма параметров (объект опций у выгрузки).
- Какие функции — в `router/testing`, какие — в `api/testing` (по правилу зависимостей).
- Добавлять ли в дамп родителя шага. Выгрузка его отдаёт; дамп `test` при добавлении
  меняется один раз, явно, отдельным коммитом с пересборкой `bun run manifests`.

## Решения исполнителя по ходу дизайна (на сверку владельцу)

- Ядро выводит виды только из своих классов: Handler (эндпоинт), Meta (пустой классовый шаг),
  Checkpoint (`BaseAccessController`), Input (унаследованный шаг билдеров api и
  `IDController`). Это факт иерархии ядра, а не толкование приложения.
- Описание вида `Value` в словаре ядра (`router/src/common/kinds.ts`: «вопрос по id из пути»)
  не расширяется: смысл объявленного вида задаёт приложение; документ ядра говорит это прямо.
- Экспорт баз билдеров api наружу или вывод Input внутри api без экспорта (сейчас `test`
  достаёт их обходным приёмом через фабрики).
- Имя и место документа ядра о тестировании (новый `main/docs/testing.md` или раздел
  `packages/api/readme.md` с ссылкой из `docs/readme.md`).

## Проверка

- Ядро: тесты новых функций в vitest — каждая на синтетическом нарушителе (правило ловит)
  и на чистом роутере (нарушений нет).
- `test`: тесты-свойства P1, P2, P6, P7, P8, P9 вызывают функции ядра; пороги «поиск жив»
  прежние; дамп побайтно прежний (или изменён одним явным коммитом, см. выше).
- `bunx vitest run`, `bun run build`, smoke; в `test` — `bun test`; `../verify.sh --fast`.
