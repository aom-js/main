## Требования

Фреймворк должен позволить следующие возможности:

- [ ] создание монолитов за счет веб-фреймворка, позволяющего делать контроллеры API, выполняющие соответствующие обработки данных, включая генерация OpenAPI-схемы
- [ ] создание микросервисов за счет использования изоляторов, а также процедуры выгрузки из создаваемого API оберточных классов и схем данных, которые позволят структурно взаимодействовать с данными из разных репозиториев, подчиненных одной логике
- [ ] непривязанность к http-фрейморкам: то есть требуется обеспечить механику, которая позволит прокидывать внутрь контроллеров любой исходный контекст, отделив в нём доступ к требуемым секциям: query, body, header, cookie, session и т.д., и обеспечивающее соответствующе включение middleware, которые могут быть в том числе взяты в виде библиотек из стека `koa`, `express` и других
- [ ] непривязанность к механике генераций структур: то есть требуется обеспечить возможность использовать в качестве схем данных произвольно взятые механики - zod, class-validator, typebox и прочие - чтобы получить на выходе типичную jsonschema-конструкцию, которую можно будет использовать повторно в другом месте как в "сыром" виде, так и пропустив реверсивно через требуемое типирование
- [ ] наличие типовых инструментов, которые позволят из коробки создавать подходящие контроллеры и сопутствующие им проверки данных, включая разделение применений в зависимости от используемых обработчиков структур (zod, typebox, class-validator, и т.д.)
- [ ] весь код хранится в монорепозитории, а публикуется в npm за счет модуля `lerna`
- [ ] код-генерация

## Что будет изменено

Само ядро должно стать значительно легче. Максимум, что должно быть использовано, это `rxjs`, `openapi3-ts` и может быть `lodash`. Все механики типа `class-validator-jsonschema` и прочие генерации должны являться расширениями, которые устанавливаются там же, где подключается конкретный веб-фреймворк и правила извлечения `body`, `query` и другие.

Для установки, извлечения и переноса мета-данных должны быть использованы свои собственные типичные конструкции, которые облегчат процедуру написания этих самых мета-установок.

### Контроллеры

Все декораторы, которые способны впускать в себя какие-то типы, типа `@This`, надо делать с аргументацией от функции: `@This(()=>OrderID)`. Это позволит уйти от ref-контейнеров там, где они не нужны, и в случае появления циклических ссылок позволит корректно обращаться к релевантным значениям, не боясь что оно не будет инициировано на моменте объявления.

### Генерация OpenAPI

Следует сделать свой декоратор, обозначающий сцепку типов, который будет корректно формировать `$ref` значения в соответствующей схеме. То есть по сути в случае использования того же `class-transformer` это будет означать наличие дополнительного декоратора, который будет повторять `@Type()`, однако что также можно будет свести к тому, чтобы сделать обобщённый декоратор, который будет одновременно вызывать связующий декоратор `@aom`, и `@ValidateNested` и `@Type` для релевантного типирования.

### Типирование

Всё типирование должно идти от интерфейсов, которые будут в конечном счете имплементироваться в схемы и прочие места. Это позволит использовать типы в тех местах, где надо избегать циклических ссылок. А также при необходимости позволит их выгружать готовыми модулями с определениями, которые можно будет использовать повторно.

### Изоляторы

Собственные декораторы, которые по сути повторяют то же, что я делаю за счет контейнер-класса. При том, что в идеале надо уметь использовать их как за счет импорта отдельных элементов, так и за счет вызова обобщённого класса, внутри которого будут методами использоваться отдельно взятые функции.
В изоляторы также будут добавлены механики связанные с тем, чтобы при их инициации указывать, какими инструментами происходит собственно обмен данными, то есть в идеале не быть привязанными к конкретной шине, а давать внятный интерфейс спуска и поднятия данных.
