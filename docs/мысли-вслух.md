# Концептуальные размышления

> **Черновик автора — исторический документ:** мысли на момент проектирования, а не описание текущего кода. Модель метаданных сейчас — [`packages/core/readme.md`](../packages/core/readme.md); расхождения заметок с кодом — [`architecture.md`](architecture.md#расхождения-с-историческими-заметками).

Что для меня в текущей ситуации выглядит немного неестественно и напрягающе? Ответ прост: постоянное взаимодействие со значениями `constructor`, `property` и иногда `descriptor`, для которых надо соответствующим образом создавать карту мета-данных, и в некоторых случаях ещё иметь возможность её копировать, а также подменять в ней контекст.

Чем это можно заменить, чтобы это было более естественной с точки зрения разработки механикой, и что в последующем можно было бы использовать в качестве инструмента более высокого порядка для другого типа решений подобного рода?

Рассмотрим эту ситуацию со следующей стороны, например, через создание соответствующего класса, который бы занимался обслуживанием и хранением метаданных в соответствующих map-структурах.

При этом сам класс подвязывается исключительно к конструктору, и может быть вызван каким-то сопутствующим нативным методом.

Как это можно выглядеть?

```ts
export function Middleware() {
  return aom.methodDecorator((decoratedConstructor, origin) => {
    //
    // и тут уже можно работать с классом, из которого всегда можно сослать на оригинальный конструктор
    // и через который уже создавать и обогащать соответствующие мета-окружения
    // и даже более того, получить хорошую механику отладки
  });
}
```

Таким образом, следует понять, как будут устроены методы, которые позволят делать соответствующую механику

```ts
class aom {
  static methodDecorator(handler) {
    return function (constructor, property, descriptor) {
      const origin = { constructor, property, descriptor };
      const decoratedConstructor = aom.define(constructor);
      return handler(decoratedConstructor, origin);
    };
  }
}
```
