# Отложенные вычисления

Итак, я сталкиваюсь с проблемой, что на стадии использования ряда декораторов возникает конфликт определений. То есть ряд процедур требует уже установленных признаков на тех или иных сущностях, в то время как по факту они там появляются позже.

Задача решается за счет создания отложенных вызовов декораторов. При этом на деле они должны иметь два варианта запуска: мгновенный и отложенный.

Решение находится в том, как вызывать соответствующие методы декорирования, где на основании наличия второго аргумента, означающего отложенный вызов, происходит фиксация релевантных аргументов, которые будут применены в момента исполнения.

При этом следует понимать, что вызов отложенных процедур должен иметь возможность запускать соответствующий каскад, и при этом не входить в рекурсию.

Скорее всего механика будет сводиться к тому, что вся магия будет происходить в методе класса, типа `Controller`, `Isolator` и так далее, который по общей логике вызывается последним, и в нём можно сделать соответствующий запуск исключительно собственных отложенных вычислений.

Начнем в целом с того, что определим соответствующие последовательности действий.

Итак, часть задачи решилась за счет того, что я всю инициацию, какую-бы то ни было, перенес на транспортируемые вызовы, передача контекста в которых на 100% решает задачу с наследованием в контроллерах.

При этом наиболее корректным способом запуска lazy-декораторов является использование setTimer, который срабатывает после того, как пройдут все миграции и наследования. Но это порождает проблему второго порядка: а именно тот факт что их вызов происходит уже после того, как инициированы все роутеры. Что обязывает изменить логику тех самых роутеров, переделав их по принципу, в котором вызов отложенного метода динамически изменяет соответствущую цепочку в объекте, который является точкой вызова.

То есть, что надо переделать?

Надо при создании роутеров переделать процедуру слияния соответствующих узлов, чтобы в моменте, когда в них происходило релевантное событие, они могли "стрельнуть" в указанные списки/методы, и там применить имеющиеся данные.

Как это может выглядеть?

Итак, я начинаю собирать роутер. На вход я подаю root, для которого при этом сами bridges уже должны быть установлены, таким образом, что они вынимаются из lazy-декораторов.

При этом на каждой итерации мне надо из ендпоинта создавать роутер, и связывать с его ендпоинтами, которые перечисляются. И даже при этом у меня ещё нет миддлварей, которые были установлены. При этом особенность процедуры такова, что последовательность, в которой миддлвари эти операции будут активироваться в общем случае будет случайной, однако порядок их установки будет каждый раз в той последовательности, в которой они указаны внутри конкретного `@Use`, и следует также иметь ввиду, что теперь за счет асинхронного запуска порядок определения декораторов не играет особой роли, то есть конкретные цепочки должны быть указаны в одном вызове, чтобы гарантированно исполниться.

Однако, подразумеваем, что я разрешаю себе делать асинхронный запуск. Что при это будет происходить?

Вот у нас есть ендпоинт, у которого есть некий родитель. У этого родителя могут быть свои собственные миддлвари, которые могут иметь свои собственные миддлвари, которые могут появиться "внезапно!", и которые надо суметь в конечном счете поставить в нужные места.

Допускаем, что установка миддлварей происходит через метод, в который они пушатся, и где может быть их релевантная фиксация.
Таким образом необходимо составить карту отсылок конкретных AomHttpElement в те маршруты, которые создаются. Как это может быть вообще сделано?

Сейчас это выглядит вот таким образом:

````ts
    // объединим миддлвари
    cursors.push(...root.element.middlewares.map(($) => new AomCursor($, path)));

    root.element.endpoints.forEach((endpoint) => {
      endpoint.path = resolve(join(path, endpoint.path));
      const route = new AomRoute(endpoint, cursors);
      this.routes.push(route);
      this.routesMap.set(`${endpoint.method}:${endpoint.path}`, route);
    });

    root.element.bridges.forEach((bridge) => {
      this.build(bridge.next, cursors, resolve(join(path, bridge.prefix)));
    });
    ```
````

Здесь надо понимать, что курсоров ещё нет, но связи уже делать надо. Таким образом следует создавать для AomRoute цепочку тех узловых точек, которые используются для формирования соответствующих связей.

Переделаю процедуру сборки на следующую:

```ts
  build2(root: AomHttp, bridges: AomHttp[] = [], prefix: string = "/") {
    bridges.push(root);

    root.element.endpoints.forEach((endpoint) => {
      // endpoint.path = resolve(join(prefix, endpoint.path));
      const route = new AomBridgedRoute(prefix, endpoint, bridges);
      this.bridgedRoutes.push(route);
      // this.routes.push(route);
      // this.routesMap.set(`${endpoint.method}:${endpoint.path}`, route);
    });

    root.element.bridges.forEach((bridge) => {
      this.build2(bridge.next, bridges, resolve(join(prefix, bridge.prefix)));
    });
  }
```

Итак, теперь у меня есть некий endpoint, внутри которого есть доступ к `$`, являющийся соответствующим AomHttp значением. Для которого я теперь могу составить первичную карту ассоциаций. При этом соответствующую карту я могу делать в обе стороны. То есть как указывать у конкретного ендпоинта, в какие бриджи он входит, так и говорит конкретным узлам, какие у него есть потомки.

Но чтобы это понять, следует двигаться от обратного. Итак, у меня есть возможность как-то пробрасывать связи между узлами. При этом сначала образуются базовые связи, а затем в них заливается то, что мне нужно, чтобы получилась красивая картинка. При этом я не всегда знаю, когда закончатся все вычисления, но подразумевается, что их сборка практически мгновенная.

То есть, рассмотрим ситуацию со следующих сторон:

1. у меня есть синхронная процедура создания роута `AomBridgedRoute`, создание которое происходит с указанием всех ключевых узлов, которые в конечном счёте составляют этот самый роут.
2. в общем случае этими элементами являются бриджи и конечный ендпоит, каждый из которых может иметь своё собственное окружение миддлварей, которые могут иметь своё собственное окружение миддлварей, инициация которых происходит непоследовательно.
3. Более того обнаруживается следующий смысловой артефакт, что использование миддлварей в прямом директивном указании, то есть в виде `@Use(Route.Mid1, Route2.Mid2, ...)` в случае применения наследуемых вызовов будет обращаться к определению, полученного из самого раннего предка. Таким образом, что в идеале и эту логику имеет смысл пересмотреть. Рассмотрю это решение чуть позже, так как он в целом не противоречит тому, что надо сделать.

Итак, у нас появляются миддлвари, которые обрабатываются соответствующей процедурой `addMiddlewares` в `AomHttpElement`, тем самым давая возможность их оттуда перехватить и направить в релевантные маршруты. Но при этом надо понимать, что порядок появления этих самых миддлварей в этих вызовах будет в общем случае непоследовательное, и часть из значений может появиться у сущности, которая еще не входит ни в один маршрут, но когда ей создадут такую ассоциацию, она должна корректно прокинуть имеющиеся у неё значения в соответствующие участки.

Какая организационная логика может решать данную задачу?

Допустим, у каждого AomHttpElement есть некая сущность под названием `relationMap`, внутри которой находятся связи с вышестоящими сущностями, возможно даже в виде указания конкретного метода этой сущности, который будет ожидать какое-то значение. При этом появление какого-то нового значения будет приводить к полному перерасчету всей цепочки на самом высоком уровне применения.

Допускаем, что это будет некий класс `AomRouteMap`, который будет создаваться для каждого роута, при этом внутри него не обязательно держать отсылку на сам роут, так как это не принципиально. Этот Map должен быть виден на уровне AomHttp и сопутствующих элементов, так чтобы не перекрывать области видимости. И этот элемент будет являться тем самым связующим звеном, внутри которого происходят сопутствующие перерасчеты и назначения. Включая, по всей видимости, присваивание маркеров.

Как данный класс должен быть организован и что он вообще должен делать? В первую очередь он должен выстраивать очереди обработки соответствующих элементов, исходя из того, в каком порядке там оказались уже имеющиеся элементы.
При этом очередь может формироваться как за счёт Use-конструкций, создавая предварительные значения, так и за счет UseNext - создавая последующие значения.

Распишу по шагам вероятную цепочку того, что будет происходить. При этом, что характерно, организационная логика конструкций такова, что за счёт своей повторяемости друг в друге произвольно взятые ключевые вычисления происходят один раз, и затем могут быть использованы повторно. То есть, если что-то расширило соответствующую связь, то оно видно сразу во всех ассоциациях.

Попробую сделать задуманное.

Шаг 1.
Создаётся роут, в нём, например 2 элемент: корневой контроллер и собственные ендпоиты текущего контроллера. Это в принципе минимальная конфигурация, которая может быть. Каждое последующее погружение будет создавать еще два элемента: мостовой элемент (контроллер или метод) и ендпоинт. Соответственно, все маршруты выглядят так: каскад мостовых элементов + ендпоинт.

При этом поскольку бридж может не содержать собственных ендпоинтов, и быть сугубо контейнеров для миддлварей, то это надо тоже учитывать.

При этом первый шаг всегда синхронный, и все последующие расширения будут происходить после.

Шаг 2.
Следует сделать какой-то диспетчер вызовов, который позволит унифицированным образом создавать структуры для отложенных и триггерных декоративных процедур.

## Рефакторинг миддлварей.

Что напрашивается? Поскольку всё теперь перекраивается на lazy-evaluations, то напрашивается логика где миддлварь будет контейнером для других миддлварей. То приводим всё к тому, что их применение - это вызов одной контейнеризированной функции, которая сама по себе может вернуть соответствующий каскад вложенных миддлварей, а также может окружить себя предварительными мидллварями, которые будут расширять соответствующий контекст.

То есть как это может выглядеть?

```ts
class Route {
  @Middleware()
  static async SomeAction() {}

  static SomeBaseMiddlewareContainer() {
    return [this.SomeAction];
  }

  @Use(() => Route.SomeBaseMiddleware())
  @Get("/")
  static async Wtf() {
    //
  }
}
```

При этом такой подход на 100% решает и вопрос, связанный с наследованием декораторов, однако не решает вопрос с тем, что вызываемый конструктор при наследовании оперирует контекстом совсем другого класса (в общем случае - родительского).

В старой версии aom это решалось когда я создавал списоку курсоров конструкцией вида

```ts
if (cursor.origin.constructor.prototype instanceof cursor.constructor) {
  Object.assign(cursor, { constructor: cursor.origin.constructor });
}
```

Что, по всей видимости, мне имеет смысл повторить у себя. Осталось только понять, что в данном случае будет являться аналогом origin значения, и как корректно выполнить такую замену. И, что самое главное, где её следует корректно выполнить.

Для этого вернёмся к началу, и в целом восстановим логику, где я не делаю отложенных вызовов, а работаю со значениями миддлварей в моменте.

Ок, это работает.
